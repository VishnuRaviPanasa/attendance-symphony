1The one-minute answer

They are not the same tool, and they are not competitors — they sit at two different points of the same pipeline.

  • Spec Kit (by GitHub) is about defining the work: turn an idea into a precise specification, a plan, and a task list — before code is written. It removes ambiguity.
  • Symphony (by OpenAI) is about executing the work: take tickets and coordinate a fleet of AI coding agents to build them in parallel, all the way to Pull Requests.
The mental model that makes it click

Neither one writes code with its own "brain." Both are conductors; the actual code is typed by a coding agent (Claude Code, Codex…), the musician.

Spec Kit conducts one musician from a written score, with you in the loop. Symphony conducts a whole orchestra from a ticket backlog, on its own.

2Spec Kit, in depth

Spec Kit is GitHub's open-source toolkit for Spec-Driven Development (SDD). The core idea: the specification is the source of truth, not the code. You get the requirements crisp first, and the implementation follows from them.

The workflow

Spec Kit installs a small CLI and adds a set of slash-commands into your AI coding agent. You move through ordered phases:

/constitution/specify/plan/tasks/implement
  • /constitution — the project's non-negotiable principles & guardrails.
  • /specify — the what & why: user stories, behaviour, acceptance criteria (no tech yet).
  • /plan — the how: tech stack, architecture, constraints.
  • /tasks — break the plan into small, ordered, actionable tasks.
  • /implement — the coding agent executes the tasks and writes the code.

It is agent-agnostic — it works with Claude Code, GitHub Copilot, Cursor, Gemini CLI and others.

What Spec Kit itself produces

Documents — a spec, a plan, a task list (markdown in your repo). The code appears at /implement, and it is written by the coding agent, not by Spec Kit's own engine.

3Symphony, in depth

Symphony is OpenAI's open-source orchestration framework for AI-driven software development. It treats an issue tracker as the control plane: it watches for ready tickets, spins up an isolated workspace per ticket, dispatches a coding agent to each, runs tests, opens a Pull Request, and reports back — with human oversight.

The lifecycle

Each ticket moves through internal claim states, and each agent run streams through execution phases:

UnclaimedClaimedRunningRetryQueuedReleased
PreparingWorkspaceBuildingPromptLaunchingAgentProcessInitializingSessionStreamingTurnFinishing

What makes it "orchestration"

  • Parallelism with backpressure — a max-concurrency cap; extra tickets queue until a slot frees, so it won't overwhelm CI or hit rate limits.
  • Isolated workspaces — each ticket runs in its own sandboxed directory.
  • Proof of work — tokens used, runtime, CI status, PR link, complexity.
  • Reconciliation — if a ticket becomes terminal, the agent is stopped and the claim released.
What Symphony itself is (and isn't)

It is not an AI model. Like Spec Kit, it's a conductor: it coordinates coding agents (the reference implementation drives Codex via an app-server) that do the actual code. The reference implementation is written in Elixir (chosen for supervising many concurrent processes).

Both ultimately reach real code — but through an agent, not by themselves.

The sharp distinction

It isn't "planning vs. code" — both can end in code. It's single-agent-guided (Spec Kit, you in the loop) vs multi-agent-autonomous (Symphony, hands-off).

This is where they differ most in practice — and it trips up most audiences.

Key point about Symphony

Symphony is not a plugin for your IDE or for Jira — it's a standalone orchestrator you deploy. You either run OpenAI's Elixir version, or implement the spec yourself in any language. (The Node backend in this project is exactly that — a working, roll-your-own Symphony-style service.)

7Jira integration

Jira is not embedded into Symphony — Jira is a task source. There is no official, out-of-the-box Jira integration; a team wires it up. Three common ways:

  • REST API (polling) — read tickets (/rest/api/3/search), update status, add PR-link comments. Simple, works everywhere.
  • Webhooks (push) — Jira notifies your orchestrator the instant a ticket is created/updated. More efficient than polling, but needs a reachable endpoint.
  • MCP — for Claude Code: attach a Jira MCP server and just say "Implement KAN-7."

Auth: a Jira API token + Atlassian email (or OAuth for large orgs). An API token is not an LLM key — it's free.

New / assigned ticket in Jira
Orchestrator reads it (REST / webhook / MCP)
Agent claims it → writes code → tests → PR
Write back: comment + move To Do → In Progress → Done

8Claude Code + MCP — the no-API-key path

This is the most important practical takeaway for your setup.

You don't need an LLM API key

Because you use Claude Code, Claude Code is the coding agent. Attach a Jira MCP connector, say "Implement KAN-7", and Claude fetches the real ticket and writes the real code — no separate API key required.

When do you need a key? Only for the fully autonomous version — a background Symphony daemon whose server calls an LLM on its own, unattended. That's the difference:

Spec Kit in Claude CodeYou, spec-firstNo

Simulated demo dashboardNobody — it's a visualNo

9How Symphony differs from CrewAI / LangGraph

All are agent-orchestration tools, but the focus differs:

  • CrewAI / LangGraph — general-purpose multi-agent frameworks (support bots, research assistants, automations).
  • Symphony — purpose-built for software engineering: coding, testing, reviews, PRs, repository management, ticket → PR.

Analogy for the talk: Agile is to Jira as AI-driven development is to Symphony — the approach vs. the tool that operationalizes it.

10Using them together

The strongest workflow uses both — good specs in, so the agents don't guess:

Product idea
Spec Kit → detailed spec + task breakdown
Generate Jira tickets from the tasks
Symphony (or Claude Code via MCP) → agents implement
Code + tests + Pull Requests → review

Spec Kit answers "what to build." Symphony answers "how to build & deliver it." Without a good spec, agents inherit ambiguity; Symphony shines when it's executing against a clear one.

11Starting a project — how do you actually use it?

A common first assumption is that you can "prompt Claude to use Symphony." You can't — Symphony is not a mode or command inside Claude Code; it's a separate service you run. So "using Symphony on a project" means one of two very different things.

Path A — Run the real Symphony framework (autonomous fleet)

This is real Symphony, and it's infrastructure setup, not a prompt:

Stand up the service — OpenAI's Elixir reference impl, or a custom orchestrator
Configure — Jira credentials, repo, concurrency, which coding agent, which tickets
Start the daemon — it polls the tracker
Feed it tickets — from Spec Kit, your PM, or manually
It auto-dispatches agents → code → tests → PR → updates the ticket
Humans review & merge the PRs
This path needs an LLM API key

The autonomous agents call an LLM on their own, so a running Symphony daemon needs an LLM key / agent runtime. That's exactly the part being simulated in the demo dashboards.

Path B — Claude Code + MCP (recommended · no API key)

You don't run the daemon. You get the same ticket → code → PR outcome with Claude Code as the agent and you as the conductor:

Open your repo in Claude Code
(Optional) Spec Kit — specify init → /specify → /plan → /tasks
Enable the Jira (Atlassian) MCP connector — one-time authorize
Prompt: "Implement KAN-7" → Claude fetches the ticket & writes the code
Review → commit / PR (keep the live board open for the demo)
Why Path B needs no key

Claude Code itself is the coding agent. You're not paying a server to call an LLM in the background — you're driving one agent interactively.

Bottom line

The closest thing to "prompt Claude to use Symphony" is prompting Claude to implement a ticket via MCP. It isn't literally running Symphony, but it delivers the ticket→code result Symphony is known for — without the service or the key.
